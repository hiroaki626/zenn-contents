Zennで技術記事を書きたいなとはずっと思っていたんですが、正直なところ、環境構築がめんどくさくてずっと放置してました。ターミナルを開いて`npm`とか`git init`とかやるのは自分にはよくわからない世界で、手をつけられずにいたんですよね。

今回、Claude Codeに全部お願いしてみたところ、あっさり終わってしまいました。ただ、その過程でAIツールの使い分けについて試行錯誤があったので、そのへんも含めて記録として残しておこうと思います。

## 自己紹介

MBKデジタル（三井物産子会社）でデータアナリストをしています。2年目です。ふだんの仕事はBigQuery × GCPベースでクライアント向けのデータ分析コンサルをやっています。SQLやBIツールは使うんですけど、ターミナルで何かをインストールしたりgitを操作したりっていうのは正直ほとんどわかっていないです。

## なぜZennで書こうと思ったか

仕事で学んだことを自分の言葉で書いてみたいなと思ったのがきっかけです。ふだんの業務でわかった気になっていることも、いざ記事にしようとすると「あれ、ちゃんと説明できないな」ということが結構あって。そういう穴に気づくために、技術記事を書いてみるのはよさそうだなと。

Zennを選んだのは、エンジニアの読者が多くて、技術的な話がちゃんと届きそうだったからです。書いていきたい方向は大きく3つあって、AIの実務活用、BigQuery/GCPまわりのデータ分析設計、データアナリストのキャリアについてです。

ただ、自分は義務になった瞬間にやらなくなるタイプなのは自覚してるので、まずは仕組みだけ作っておいて、書きたくなったら書くというスタンスでいこうかなと。この記事自体がその第一歩というか、仕組みづくりの記録みたいなものです。

## Claude Codeとは

ターミナルで動くAIエージェントです。日本語で「○○して」と指示すると、実際にコマンドを実行したりファイルを作ったりしてくれます。ブラウザ版のclaude.aiとの違いは、PC上で実際に手を動かせるというところですね。説明はこのくらいにして、やったことを見せたほうが早いと思うので、次に進みます。

## 実際にやったこと

Claude Codeに渡した指示はこれだけです。

```
Zennで記事を投稿するための環境をゼロから構築して。
GitHubのリモートリポジトリはここ：
https://github.com/hiroaki626/zenn-contents
```

ここから先は、Claude Codeが自分で判断しながら進めてくれました。

#### ① Node.jsのインストール

```bash
winget install OpenJS.NodeJS.LTS
```

Zenn CLIを使うにはNode.jsが必要らしいんですが、自分の環境には入っていませんでした。Claude Codeがそれを検知して、自動でインストールしてくれました。そもそもNode.jsが必要ということ自体を知らなかったので、素直に助かりました。

#### ② プロジェクト初期化

```bash
npm init -y
```

`package.json`が生成されます。後からClaude Codeに聞いたら「このフォルダはNode.jsのプロジェクトですよという身分証明書のようなもの」と説明してくれて、なるほどなと。

#### ③ Zenn CLIのセットアップ

```bash
npx zenn-cli init
```

`articles/`と`books/`フォルダが作られます。記事のMarkdownファイルはここに入れていく形ですね。

ちなみに最初、Claude Codeは`npx zenn init`で実行してエラーになりました。でも自分でパッケージ名の間違いに気づいて`zenn-cli`に修正して、再実行して成功しています。AIもミスするんだなと思いつつ、自分でリカバリーしてくれるのはありがたかったです。

#### ④ GitHubとの紐付け

```bash
git init
git remote add origin https://github.com/hiroaki626/zenn-contents.git
```

ローカルフォルダとGitHubリポジトリを接続するステップです。

#### ⑤ GitHubへプッシュ

```bash
git add .
git commit -m "chore: Zenn執筆環境をセットアップ"
git push -u origin master
```

ここまで来れば、GitHubにpushするだけでZennに自動デプロイされる状態です。

---

振り返ると、自分がやったのは「最初の指示文を書く」「実行確認でyを押す」「GitHubのURLとメールアドレスを聞かれたので答える」の3つだけでした。え、もう終わったの？というのが正直な感想で、ちょっと拍子抜けしたくらいです。AIがなかったらたぶんずっと放置してたので、自分みたいに腰が重い人にはかなり合ってるやり方なのかもしれないです。

## 「今やったことを説明して」と聞いてみた

一通り終わった後、コマンドの意味が全然わからなかったので、Claude Codeにそのまま聞いてみました。

返ってきた説明がわかりやすくて、地味に嬉しかったです。

- `npm init` → 「このフォルダはプロジェクトですよ」という**身分証明書**を作る
- `git add` → 保存したいファイルを**封筒に入れる**
- `git commit` → 封筒に**日付と内容を書く**
- `git push` → 封筒を**郵便ポストに投函する**

gitの操作って、自分は正直あんまりわかっていなかったんですよね。こうやって比喩で返してもらえると、やっと腑に落ちるというか。

「実行してもらった後に、なぜそうしたかを聞ける」という流れは、思ったよりよかったです。作業と学習が同時に進むような感覚がありました。

## claude.ai × Claude Code——結局2つ使うことになった

ここがこの記事で一番書きたかったところです。

実はこの記事の構成、Claude Code（ターミナル版）ではなくclaude.ai（ブラウザ版のチャット）と壁打ちして作っています。

最初はClaude Codeに「記事の構成を考えて」と頼んでみました。出てきた案はまとまってはいたんですけど、自分の状況とズレていたんですね。全体的に初心者向けに寄りすぎていたり、自分が一番書きたいことが構成に入っていなかったり。こういう微妙なズレの調整が、Claude Codeだと難しかったんです。

理由はたぶんシンプルで、Claude Codeは毎回セッションがリセットされるからですね。「自分がなぜZennで書くのか」とか「どういう読者に届けたいのか」みたいな文脈を持っていないので、どうしても汎用的な提案になってしまう。

一方で、claude.aiには過去の会話の蓄積があって、自分の仕事内容とか発信の方向性とか、性格（義務にすると続かないタイプ）まで踏まえた上で構成案を出してくれました。同じ「Claude」なのに、文脈があるかないかでアウトプットがけっこう変わるんだなと。

使い分けを整理するとこんな感じになるかなと思います。

| ツール | 向いていること |
|--------|----------------|
| claude.ai | 戦略・構成・レビュー（何を書くか、どう届けるか） |
| Claude Code | 実行・ファイル操作・デプロイ（実際に作る、コマンドを打つ） |

これ、自分のふだんの仕事でも似たようなことがあるなと思っていて。「クライアントの課題に対してどんな問いを立てるか」と「SQLを書いて分析を回す」って、自分の中でもけっこう別の作業なんですよね。AIに頼むときも、同じような分け方をしたほうがうまくいったという感じです。

## 方向性のズレを直す——claude.aiとの壁打ちで起きたこと

使い分けの話をもう少し具体的に書いておきます。

構成だけじゃなく、記事の方向性自体にもズレがありました。Claude Codeが最初に出してきた構成案は「はじめに → 自己紹介 → Claude Codeとは → 手順 → 感想 → まとめ」みたいな、セットアップ記事としてはよくある形だったんですけど、自分が一番書きたかった「AIの使い分け」の話が構成のどこにもなかったんですね。

claude.aiに同じことを頼んだら、「この記事の差別化ポイントはclaude.aiとClaude Codeの使い分けの話であって、セットアップ手順は他の記事と被る」という指摘が返ってきて、構成の中心が変わりました。

これは構成を考えてもらったというより、「何のためにこの記事を書くんだっけ」というところを整理してもらった感じに近かったです。Claude Codeはファイルを作るのは得意ですけど、こういうふわっとした相談はclaude.aiのほうが合ってたなというのが正直な感想です。

## 言葉遣いを自分に寄せる——AIに話し方を学ばせた

もう一つ、書いておきたい体験があります。

最初にclaude.aiが書いてくれた記事のドラフトは、内容としては悪くなかったんですけど、文体が自分っぽくなかったんですよね。「だ・である」調で、断定が多くて、なんというかすかした感じがあって。自分はふだんそういう話し方をしないので、読んでいてどうも落ち着かなくて。

で、「もっと自分の話し方に寄せてほしい」とフィードバックしたんですけど、抽象的な指示だけだとなかなかうまくいかなくて。そこで試しに、自分のクライアント向けの会議の文字起こしデータをclaude.aiに渡してみました。「ここから自分の話し方の特徴を抽出して、それに合わせて書き直してほしい」と。

返ってきた分析がけっこう的確で、「断定を避けて『〜かなと思います』で着地させる」「クッション表現（ちょっと、正直なところ）を挟む」「結論を先に言わずプロセスを見せてから着地する」みたいな特徴を拾ってくれました。それを反映して書き直してもらったのが、今読んでいるこの記事の文体です。

自分としては、AIに文章を頼むときは「カジュアルに書いて」みたいな指示だけだと足りなくて、実際の話し方のデータを渡すほうがうまくいきました。もっと良いやり方があるのかもしれないですけど、今の自分にはこれが一番しっくり来ています。

ちなみに、この文体ルールはCLAUDE.mdにも追記しておいたので、今後Claude Codeに記事を書かせるときにも同じトーンで出てくるはずです。ここもclaude.aiで整理した内容をClaude Codeに渡す、という使い分けの一例ですね。

## まとめ

環境構築自体はClaude Codeに任せればあっさり終わります。ただ、大事なのはその先で、何を書くか、誰に届けるか、なぜ書くのか。そこはAIに丸投げしても答えが出てこなくて、自分で考えるか、文脈を共有した相手と壁打ちするしかないのかなと思っています。

今後書いていきたいのは、BigQuery × GCPの実務設計、Vertex AIの現場での使いどころ、データアナリストのキャリア設計あたりです。

続けられるかはわかりませんが、自分のペースで書いていければいいなと思っています。
